# A2 · Agent 化：让模型自己决定查不查

A1（v0.5）解决的是「怎么查得准」。A2 换的是**控制方式**：

- A1：用户打字 → 固定流水线（关键词 + 向量）→ 出结果。
- A2：用户说话 → 模型判断要不要查、查什么 → 看到结果再回答。

同一份数据，两种控制方式。这就是「检索增强」和「Agent」的分界线。

## 三个工具

| 工具 | 什么时候该调 | 实现 |
|---|---|---|
| `search_memory` | 问「谁说过…」「上次那个…」 | `search.search_all(conn, q, "message", ...)`，hybrid |
| `search_meme` | 想发表情、问「有没有…的图」 | `search.search_all(conn, q, "meme", ...)`，hybrid |
| `get_time` | 问今天几号 / 几点 | 直接读服务器时间，不查库 |

只有三个，是故意的。工具越多，模型越容易乱调。

## 循环怎么转

```
用户问题 → 模型
            ├─ 不要工具 → 直接回答（结束，0 轮）
            └─ 要工具 → 执行 → 结果喂回 → 模型
                         ├─ 够了 → 回答（结束）
                         └─ 还要 → 再来（最多 3 轮，超了就停）
```

代码在 `app/agent.py`，`run()` 就是这个循环。三个刻意的限制：

1. **最多 3 轮**。再多只是在烧 token，通常意味着问题本身没问清楚。
2. **工具结果截断**到单条 120 字、最多 5 条。工具输出会挤占上下文，不加限制迟早把窗口顶爆。
3. **截断轮次时报错而不是假装完成**。超轮时会返回 `"（工具调用超过 N 轮，我先停下来…）"`，
   并在 trace 里留一条 `STOP`。宁可难看，也不要让「它以为自己做完了」。

## 试用入口

`https://zkysever.com/agent`（和主页面共用同一道口令）。

页面会同时显示三样东西：回答、**调了几次工具**、每次的工具名 / 参数 / 命中的条目。
第三样才是重点 —— 它让你能挑错，而不只是看结果好不好。

|---|---|---|---|

## 下一步要评的东西（A2 真正的验收）

不是「回答像不像人」，而是这三类错误各自的比率：

1. **过度调用**：一句话就能答的问题，却去翻库（例：「你好呀」）。
2. **该调不调**：明明该查，却凭印象编。
3. **指代消解**：「那个」「他说的」「上次那个」到底指哪句 —— 目前基本靠运气。

做法：攒 30 条真实会问的话，逐条标「该调哪个工具 / 该调几次」，然后跑一遍统计：
正确率 ≥ 24/30、误触发 < 15%。评测集放 `eval/agent_cases.jsonl`，脚本是
`scripts/run_agent_eval.py`（`--grep` 只跑挂掉的几条，子集不判定达标）。

### 已经跑完的结果（2026-11-09）

| 轮次 | 正确率 | 误触发 | 平均轮数 | 平均耗时 |
|---|---|---|---|---|
| 首轮 | 26/30 = 0.867 | 0/6 | 1.03 | 3986ms |
| 定稿 | 30/30 = 1.000 | 0/6 | 1.03 | 4081ms |

首轮那四条失败拆开看：2 条是 `SSLError: Max retries exceeded`（网络，已加重试），
1 条是我评测集写错（「昨天」必须先知道今天几号），1 条是真的过度调用。
**30/30 说明这套题已经饱和，不说明它好用** —— 下一步要加难 case：不出现原词的说法、
指代、聚合问题（「谁最常说话」现在工具集里没有 SQL，大概率会错，错得留着）。
细节和五条结论见 `EVAL.md` 第七节。
## 上下文：让「刚才那句」有东西可指（A2 v0.2，2026-11-10）

A3 的路由实验里，四个方案（20 行正则 / 免费小模型 / DeepSeek / 分级路由）在三条指代题上
**错法一模一样**。这说明问题不在模型，在接口：`/api/agent` 一次只收到一句话，
「刚才那句话是谁说的」里的「刚才」在服务端根本不存在。

### 接口

```
GET /api/agent?q=…&history=[{"role":"user","content":"…"},{"role":"assistant","content":"…"}]
```

- `history` 是 URL 编码后的 JSON 数组，可以不给（不给就是老的单轮行为）。
- `_norm_history()` 会洗一遍：只认 `role` / `content`；`role` 白名单只有 `user` / `assistant`
  （不然一个特制请求就能冒充 `system` 把规则改掉）；单条截 200 字；只保留最近 3 轮。
- 前端 `web/agent.html` 里一个 `HISTORY` 数组，每次问完把「问了什么 / 答了什么」push 进去，
  只带对话本身，**不带工具轨迹**——带着只会让上下文变贵、变乱。

### 结果

| | 6 条上下文题 | 误触发 | 平均耗时 |
|---|---|---|---|
| 不给上下文 | **0/6** | 1/5 | 3322ms |
| 带最近 3 轮 | **6/6** | 0/5 | 2948ms |

复现：`python scripts/run_agent_eval.py --cases eval/agent_history_cases.jsonl --no-history`

### 一个必须记住的坑

只判「工具调对没调对」的话，**不给上下文也能得 4/6**——模型很乖地回一句
「你说的是哪句？我这边没有上下文」，工具层面零调用、完全正确，答案全是废的。
所以这批判定给 case 加了 `expect_any`（回答里必须出现指定关键词）。
**指标选错，实验会得出反向结论。**

### 现在的限制（2026-11-10 时点，已被 2026-11-12 的记忆升级部分解决）

- ~~上下文只活在浏览器内存里，刷新即失忆~~ → **已改**：现在按 session 存服务端（见最后一节）。
- ~~只带最近 3 轮~~ → **已改**：默认 20 轮，可用 `AGENT_HISTORY_TURNS` 调。
- 仍然解不了「上周那个谁说了什么」——那需要时间维度上的检索，不是多带几轮上下文能解决的。

## 规则前置：省掉那一次往返（A3 落地，2026-11-11）

A3 量出来「20 行正则和 deepseek 打平、但便宜 18 倍快 50 倍」，可那只是**判断该调哪个工具**。
一句话的真实成本是两趟：先问模型「你打算查什么」→ 执行工具 → 再喂回去让它写答案。
规则前置省掉的是第一趟：`app/router.py` 判定有把握，就先把工具跑了，
直接构造一轮「工具已返回」的对话让模型接着写。

### 三个前提，缺一个就不前置

1. 规则有把握（`conf == "high"`）——low 包括指代和怪用词，正是规则的短板；
2. 没带 `history`——带上下文时「刚才那句」只能靠上文解；
3. 规则确实要调工具——寒暄类工具集为空，没东西可前置。

### 第一版是错的，值得记住

第一版把预查结果当成一条 **system 消息**塞进去（「我先预查了，够了就别重复查」）。
实测 50 条里 38 条被前置，**这 38 条模型全部又自己调了一遍**——
在它眼里「还没调过工具」，system 里的字只是参考资料，不是事实。
结果既花了预查的钱，又没省下往返。

第二版改成**伪造一轮真正的工具往返**：`assistant(tool_calls)` + `tool(结果)` 消息，
模型看到的状态就是「这工具刚调过、结果是这个」，才会顺着写答案。

### 结果（50 条同一份题，2026-11-11）

| | 正确率 | 模型自己发起的工具调用 | 平均耗时 | 总耗时 |
|---|---|---|---|---|
| 不做前置 | 49/50 | 1.04 次 | 7209 ms | 375 s |
| 第一版（system 消息） | 49/50 | 1.04 次 | 更慢 | — |
| **第二版（伪造往返）** | 49/50 | **0.86 次** | **4661 ms** | **248 s** |

同样的正确率，**快 35%、模型往返少 17%**。6 条上下文题仍是 **6/6**（带 history 时不前置，实测 `前置=-`）。

### 怎么关掉 / 怎么复现

```bash
# 开关（默认开）：
AGENT_PREFETCH=0        # 关掉，行为和 v0.9 完全一致
# 复现对比：
python scripts/run_agent_eval.py --no-prefetch   # 基线
python scripts/run_agent_eval.py                 # 前置
```

前端 `/agent` 的工具记录里，前置的条目会多一个「规则前置 ·」标签——
区分它是为了看清「这类题规则已经能接住」，而不是模型变聪明了。

## 纠错记忆：同一个问题不会答错第二次（v0.13，2026-11-12）

### 为什么「学习」从纠错开始，而不是先搞「自动总结知识」

三条理由，按重要性排：

1. **信号是用户主动给的**。自动抽取（从群聊里猜「谁喜欢什么」）会自己编；「不对，应该是 X」是确定的事实。先把确定的东西用起来，再谈猜的。
2. **一次纠正终身生效，还能算命中率**。`corrections.hits` 记录这条被真正用过几次——这是「它到底学没学」唯一诚实的指标。没有这个数字，所谓学习都是嘴上的。
3. **每条纠错顺手就是一条评测题**（问题 + 正确答案）。学习和评测共用同一份数据，不会出现「评测集是拍脑袋写的、学习是从真实对话里学的」两套东西对不上。

### 数据：`corrections` 表

```sql
CREATE TABLE corrections (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ts TEXT NOT NULL,
    question TEXT NOT NULL,   -- 用户当时问的那句话，原样
    norm TEXT NOT NULL,       -- 归一化后的（去标点空白、全角转半角、小写），只用来匹配
    wrong TEXT,               -- 它当时答错的
    right TEXT NOT NULL,      -- 用户给的正确答案
    source TEXT,              -- web / qq / admin
    session_id TEXT,
    hits INTEGER NOT NULL DEFAULT 0
);
```

和 `agent_turns` 的区别要记牢：**`agent_turns` 是流水账（发生过什么），`corrections` 是结论（应该怎么答）。流水账不会改变行为，结论会。**

### 匹配：三层，从严到松，宁可漏不要错杀

`app/learn.py` 的 `find()`：

1. 归一化后**完全一样** —— 最可信；
2. **一问包含另一问**（都至少 4 个字）—— 处理「帮我代一个白系ap」vs「帮我代一个白系ap啊」；
3. **二元组互相包含** —— 处理中间多插了几个字。

都没命中就返回 `None`，老老实实走模型。为什么不用向量相似度做模糊匹配？因为这里错杀的代价不对称：漏一条纠正只是「它还是原来那样答」，错杀一条会让它**在该答对的地方答错**，比不学更糟。

### 命中之后：原样答，不让模型改写

`agent.run()` 里在调模型之前先查一次，命中就直接返回 `right`，`model="learned"`、`rounds=0`。

这是个刻意的取舍。让模型「用自己的话说一遍」听起来更自然，但纠正的语义常常很窄（「白系 AP 是《舞萌》里的一首歌」），模型会顺手补一堆自己编的细节——**那就等于没纠成**。宁可答得生硬，也不要答得流畅但错。

### 接口与界面

| 方法 | 路径 | 干什么 |
|---|---|---|
| POST | `/api/agent/fix?q=&right=&wrong=` | 教一句（同一问题再教 = 覆盖，不叠加） |
| GET | `/api/agent/fixes?limit=` | 它现在学会了哪些（带 `hits`） |
| POST | `/api/agent/fix/delete?id=` | 删掉一条 |

参数走 query string 而不是表单——服务器没装 `python-multipart`，用 `Form(...)` 会让启动直接报错，为一条纠正去加依赖不值得。

`web/agent.html` 每条回答下面两个按钮：「不对，我教它」展开输入框；「它学会的（N）」列出全部并可单条删除。**能删是必须的**：教错了要能撤，否则错误会被一直放大。

### 实测

| | 耗时 | 模型轮数 |
|---|---|---|
| 第一次问「帮我代一个白系ap」（没教过） | 4302.5 ms | 2 轮工具 |
| 教完之后问「帮我代一个白系AP啊」（多一个字） | **0.2 ms** | **0 轮** |

`scripts/selftest.py` 加了 5 项断言：归一化命中、包含命中、不会乱吃（「今天几号」不命中）、再教是覆盖不是叠加、能删。

### 三条已知短板

1. **只对它被纠正过的问题生效**。没教过的地方照样会错——这不是「学会思考」，是「记住答案」。
2. **匹配是字面不是语义**。「白系ap」教过之后，问「舞萌那首歌代打」还是不会命中。要语义得走向量，但那就回到了错杀风险。
3. **表会一直长**。现在是留最近 500 条自动淘汰；如果以后纠正量大到几千条，得改成「按命中率淘汰」（从没被用过的先扔）。

## 记忆搬到服务端（A2 v0.3，2026-11-12）

用户原话：「能不能让它自己记得，我现在有钱了，不用再删除它的记忆了。」

### 以前为什么是「只存浏览器内存」

v0.2 那版把上下文放在前端 `HISTORY` 数组里，每次请求拼成 `history=` 参数传上来。能解决指代，但三个硬伤：

1. **刷新即失忆**——关掉页面再打开，它就不认识你了；
2. **换设备即失忆**——手机上问一半，电脑接不上；
3. **客户端说的「上文」本来就不该被信任**——虽然做了 role 白名单和截断，但它终究是外部输入。

### 现在怎么存

新表（`app/db.py`）：

```sql
CREATE TABLE IF NOT EXISTS agent_turns (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    ts TEXT NOT NULL,
    role TEXT NOT NULL,     -- 只有 user / assistant
    content TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_agent_turns_session ON agent_turns(session_id, id);
```

流程：浏览器第一次问 → 服务端生成 `session_id` 并 `Set-Cookie: gb_sess`（HttpOnly）→ 每轮问答写 `agent_turns` →
下次提问从库里取最近 N 轮塞进 messages → 答完 `memory.trim()` 把超过 200 轮的老记录删掉。

`app/memory.py` 只做五件事：`new_session` / `append`（role 白名单）/ `recent` / `turn_count` / `forget` / `trim`。

### 预算放宽了多少（以前全是为了省钱）

| 项 | 以前 | 现在 | 环境变量 |
|---|---|---|---|
| 往回带几轮对话 | 3 | **20** | `AGENT_HISTORY_TURNS` |
| 单条历史截断 | 200 字 | **600 字** | `AGENT_HISTORY_CHARS` |
| 单条检索结果截断 | 120 字 | **240 字** | `AGENT_HIT_CHARS` |
| 一次工具最多几条 | 5 | **6** | `AGENT_MAX_HITS` |
| 最多几轮工具调用 | 3 | 3（故意不动） | `AGENT_MAX_ROUNDS` |

**该放宽的是「记忆」，不是「噪音」——这是量出来的，不是猜的：**

| 工具截断配置 | 50 条正确率 | 误触发 | 平均轮数 | 平均耗时 |
|---|---|---|---|---|
| 120 字 / 5 条（旧） | 49/50 = 0.980 | 0/12 | 1.04 | 7209 ms |
| 400 字 / 8 条（第一版改法） | 47/50 = 0.940 | **1/12** | 0.92 | 2885 ms |
| **240 字 / 6 条（最终）** | **48/50 = 0.960** | **0/12** | 0.90 | 2801 ms |

放到 400 字那组，多出来的一次误触发是「上一条图是谁发的」——本该反问，它却去翻库了。
工具结果越长，它越容易觉得「我该去查一下」。所以工具输出只翻一倍，历史轮数翻了六倍多。
（旧的 120/5 那行 7209ms 是关掉规则前置的基线，不能直接跟后两行比耗时。）

### 代价，说清楚

历史从 3 轮变 20 轮，prompt 会长几倍；命中截断从 120 字变 400 字，工具结果也长几倍。
**这不是免费的**，一次问答的 token 可能是原来的 3–5 倍。用户明确表示接受（「我现在有钱了」），
但所有值都能在 `.env` 里用上面那几个变量拧回去，不用改代码：

```bash
# /opt/group-brain/.env
AGENT_HISTORY_TURNS=6
AGENT_HIT_CHARS=200
```

### 留了一个能删的按钮

「不用删记忆」不等于「删不掉」。`POST /api/agent/forget` 清空当前会话，
`/agent` 页脚有个不显眼的「清空记忆」小按钮——它是保险丝，不是功能。

### 已知短板

- **表会一直长**。每个 session 最多留 200 轮、单条最多 2000 字，但没有「全局清理」定时任务；
  目前靠 `forget` 手动清。会话多了以后这张表会变成库里第二大的表（第一是向量）。
- **记忆是「这台浏览器的」**，不是「你的」。换浏览器/隐身模式就是新会话——
  要真正做到「跟人走」，得先有登录体系，那是另一个项目。
- **没做跨会话引用**：「上次我们聊的那个」只能看到本 session，老会话里的内容还得靠检索。
