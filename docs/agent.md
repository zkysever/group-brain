# A2 · Agent 化：让模型自己决定查不查

A1（v0.5）解决的是「怎么查得准」。A2 换的是**控制方式**：

- A1：用户打字 → 固定流水线（关键词 + 向量）→ 出结果。
- A2：用户说话 → 模型判断要不要查、查什么 → 看到结果再回答。

同一份数据，两种控制方式。这就是「检索增强」和「Agent」的分界线。

## 三个工具

| 工具 | 什么时候该调 | 实现 |
|---|---|---|
| `search_memory` | 问「谁说过…」「上次那个…」 | `search.search_all(conn, q, "message", ...)`，hybrid |
| `search_meme` | 想发表情、问「有没有…的图」 | `search.search_all(conn, q, "meme", ...)`，hybrid |
| `get_time` | 问今天几号 / 几点 | 直接读服务器时间，不查库 |

只有三个，是故意的。工具越多，模型越容易乱调。

## 循环怎么转

```
用户问题 → 模型
            ├─ 不要工具 → 直接回答（结束，0 轮）
            └─ 要工具 → 执行 → 结果喂回 → 模型
                         ├─ 够了 → 回答（结束）
                         └─ 还要 → 再来（最多 3 轮，超了就停）
```

代码在 `app/agent.py`，`run()` 就是这个循环。三个刻意的限制：

1. **最多 3 轮**。再多只是在烧 token，通常意味着问题本身没问清楚。
2. **工具结果截断**到单条 120 字、最多 5 条。工具输出会挤占上下文，不加限制迟早把窗口顶爆。
3. **截断轮次时报错而不是假装完成**。超轮时会返回 `"（工具调用超过 N 轮，我先停下来…）"`，
   并在 trace 里留一条 `STOP`。宁可难看，也不要让「它以为自己做完了」。

## 试用入口

`https://zkysever.com/agent`（和主页面共用同一道口令）。

页面会同时显示三样东西：回答、**调了几次工具**、每次的工具名 / 参数 / 命中的条目。
第三样才是重点 —— 它让你能挑错，而不只是看结果好不好。

|---|---|---|---|

## 下一步要评的东西（A2 真正的验收）

不是「回答像不像人」，而是这三类错误各自的比率：

1. **过度调用**：一句话就能答的问题，却去翻库（例：「你好呀」）。
2. **该调不调**：明明该查，却凭印象编。
3. **指代消解**：「那个」「他说的」「上次那个」到底指哪句 —— 目前基本靠运气。

做法：攒 30 条真实会问的话，逐条标「该调哪个工具 / 该调几次」，然后跑一遍统计：
正确率 ≥ 24/30、误触发 < 15%。评测集放 `eval/agent_cases.jsonl`，脚本是
`scripts/run_agent_eval.py`（`--grep` 只跑挂掉的几条，子集不判定达标）。

### 已经跑完的结果（2026-11-09）

| 轮次 | 正确率 | 误触发 | 平均轮数 | 平均耗时 |
|---|---|---|---|---|
| 首轮 | 26/30 = 0.867 | 0/6 | 1.03 | 3986ms |
| 定稿 | 30/30 = 1.000 | 0/6 | 1.03 | 4081ms |

首轮那四条失败拆开看：2 条是 `SSLError: Max retries exceeded`（网络，已加重试），
1 条是我评测集写错（「昨天」必须先知道今天几号），1 条是真的过度调用。
**30/30 说明这套题已经饱和，不说明它好用** —— 下一步要加难 case：不出现原词的说法、
指代、聚合问题（「谁最常说话」现在工具集里没有 SQL，大概率会错，错得留着）。
细节和五条结论见 `EVAL.md` 第七节。
## 上下文：让「刚才那句」有东西可指（A2 v0.2，2026-11-10）

A3 的路由实验里，四个方案（20 行正则 / 免费小模型 / DeepSeek / 分级路由）在三条指代题上
**错法一模一样**。这说明问题不在模型，在接口：`/api/agent` 一次只收到一句话，
「刚才那句话是谁说的」里的「刚才」在服务端根本不存在。

### 接口

```
GET /api/agent?q=…&history=[{"role":"user","content":"…"},{"role":"assistant","content":"…"}]
```

- `history` 是 URL 编码后的 JSON 数组，可以不给（不给就是老的单轮行为）。
- `_norm_history()` 会洗一遍：只认 `role` / `content`；`role` 白名单只有 `user` / `assistant`
  （不然一个特制请求就能冒充 `system` 把规则改掉）；单条截 200 字；只保留最近 3 轮。
- 前端 `web/agent.html` 里一个 `HISTORY` 数组，每次问完把「问了什么 / 答了什么」push 进去，
  只带对话本身，**不带工具轨迹**——带着只会让上下文变贵、变乱。

### 结果

| | 6 条上下文题 | 误触发 | 平均耗时 |
|---|---|---|---|
| 不给上下文 | **0/6** | 1/5 | 3322ms |
| 带最近 3 轮 | **6/6** | 0/5 | 2948ms |

复现：`python scripts/run_agent_eval.py --cases eval/agent_history_cases.jsonl --no-history`

### 一个必须记住的坑

只判「工具调对没调对」的话，**不给上下文也能得 4/6**——模型很乖地回一句
「你说的是哪句？我这边没有上下文」，工具层面零调用、完全正确，答案全是废的。
所以这批判定给 case 加了 `expect_any`（回答里必须出现指定关键词）。
**指标选错，实验会得出反向结论。**

### 现在的限制（2026-11-10 时点，已被 2026-11-12 的记忆升级部分解决）

- ~~上下文只活在浏览器内存里，刷新即失忆~~ → **已改**：现在按 session 存服务端（见最后一节）。
- ~~只带最近 3 轮~~ → **已改**：默认 20 轮，可用 `AGENT_HISTORY_TURNS` 调。
- 仍然解不了「上周那个谁说了什么」——那需要时间维度上的检索，不是多带几轮上下文能解决的。

## 规则前置：省掉那一次往返（A3 落地，2026-11-11）

A3 量出来「20 行正则和 deepseek 打平、但便宜 18 倍快 50 倍」，可那只是**判断该调哪个工具**。
一句话的真实成本是两趟：先问模型「你打算查什么」→ 执行工具 → 再喂回去让它写答案。
规则前置省掉的是第一趟：`app/router.py` 判定有把握，就先把工具跑了，
直接构造一轮「工具已返回」的对话让模型接着写。

### 三个前提，缺一个就不前置

1. 规则有把握（`conf == "high"`）——low 包括指代和怪用词，正是规则的短板；
2. 没带 `history`——带上下文时「刚才那句」只能靠上文解；
3. 规则确实要调工具——寒暄类工具集为空，没东西可前置。

### 第一版是错的，值得记住

第一版把预查结果当成一条 **system 消息**塞进去（「我先预查了，够了就别重复查」）。
实测 50 条里 38 条被前置，**这 38 条模型全部又自己调了一遍**——
在它眼里「还没调过工具」，system 里的字只是参考资料，不是事实。
结果既花了预查的钱，又没省下往返。

第二版改成**伪造一轮真正的工具往返**：`assistant(tool_calls)` + `tool(结果)` 消息，
模型看到的状态就是「这工具刚调过、结果是这个」，才会顺着写答案。

### 结果（50 条同一份题，2026-11-11）

| | 正确率 | 模型自己发起的工具调用 | 平均耗时 | 总耗时 |
|---|---|---|---|---|
| 不做前置 | 49/50 | 1.04 次 | 7209 ms | 375 s |
| 第一版（system 消息） | 49/50 | 1.04 次 | 更慢 | — |
| **第二版（伪造往返）** | 49/50 | **0.86 次** | **4661 ms** | **248 s** |

同样的正确率，**快 35%、模型往返少 17%**。6 条上下文题仍是 **6/6**（带 history 时不前置，实测 `前置=-`）。

### 怎么关掉 / 怎么复现

```bash
# 开关（默认开）：
AGENT_PREFETCH=0        # 关掉，行为和 v0.9 完全一致
# 复现对比：
python scripts/run_agent_eval.py --no-prefetch   # 基线
python scripts/run_agent_eval.py                 # 前置
```

前端 `/agent` 的工具记录里，前置的条目会多一个「规则前置 ·」标签——
区分它是为了看清「这类题规则已经能接住」，而不是模型变聪明了。

## 纠错记忆：同一个问题不会答错第二次（v0.13，2026-11-12）

### 为什么「学习」从纠错开始，而不是先搞「自动总结知识」

三条理由，按重要性排：

1. **信号是用户主动给的**。自动抽取（从群聊里猜「谁喜欢什么」）会自己编；「不对，应该是 X」是确定的事实。先把确定的东西用起来，再谈猜的。
2. **一次纠正终身生效，还能算命中率**。`corrections.hits` 记录这条被真正用过几次——这是「它到底学没学」唯一诚实的指标。没有这个数字，所谓学习都是嘴上的。
3. **每条纠错顺手就是一条评测题**（问题 + 正确答案）。学习和评测共用同一份数据，不会出现「评测集是拍脑袋写的、学习是从真实对话里学的」两套东西对不上。

### 数据：`corrections` 表

```sql
CREATE TABLE corrections (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ts TEXT NOT NULL,
    question TEXT NOT NULL,   -- 用户当时问的那句话，原样
    norm TEXT NOT NULL,       -- 归一化后的（去标点空白、全角转半角、小写），只用来匹配
    wrong TEXT,               -- 它当时答错的
    right TEXT NOT NULL,      -- 用户给的正确答案
    source TEXT,              -- web / qq / admin
    session_id TEXT,
    hits INTEGER NOT NULL DEFAULT 0
);
```

和 `agent_turns` 的区别要记牢：**`agent_turns` 是流水账（发生过什么），`corrections` 是结论（应该怎么答）。流水账不会改变行为，结论会。**

### 匹配：三层，从严到松，宁可漏不要错杀

`app/learn.py` 的 `find()`：

1. 归一化后**完全一样** —— 最可信；
2. **一问包含另一问**（都至少 4 个字）—— 处理「帮我代一个白系ap」vs「帮我代一个白系ap啊」；
3. **二元组互相包含** —— 处理中间多插了几个字。

都没命中就返回 `None`，老老实实走模型。为什么不用向量相似度做模糊匹配？因为这里错杀的代价不对称：漏一条纠正只是「它还是原来那样答」，错杀一条会让它**在该答对的地方答错**，比不学更糟。

### 命中之后：原样答，不让模型改写

`agent.run()` 里在调模型之前先查一次，命中就直接返回 `right`，`model="learned"`、`rounds=0`。

这是个刻意的取舍。让模型「用自己的话说一遍」听起来更自然，但纠正的语义常常很窄（「白系 AP 是《舞萌》里的一首歌」），模型会顺手补一堆自己编的细节——**那就等于没纠成**。宁可答得生硬，也不要答得流畅但错。

### 接口与界面

| 方法 | 路径 | 干什么 |
|---|---|---|
| POST | `/api/agent/fix?q=&right=&wrong=` | 教一句（同一问题再教 = 覆盖，不叠加） |
| GET | `/api/agent/fixes?limit=` | 它现在学会了哪些（带 `hits`） |
| POST | `/api/agent/fix/delete?id=` | 删掉一条 |

参数走 query string 而不是表单——服务器没装 `python-multipart`，用 `Form(...)` 会让启动直接报错，为一条纠正去加依赖不值得。

`web/agent.html` 每条回答下面两个按钮：「不对，我教它」展开输入框；「它学会的（N）」列出全部并可单条删除。**能删是必须的**：教错了要能撤，否则错误会被一直放大。

### 实测

| | 耗时 | 模型轮数 |
|---|---|---|
| 第一次问「帮我代一个白系ap」（没教过） | 4302.5 ms | 2 轮工具 |
| 教完之后问「帮我代一个白系AP啊」（多一个字） | **0.2 ms** | **0 轮** |

`scripts/selftest.py` 加了 5 项断言：归一化命中、包含命中、不会乱吃（「今天几号」不命中）、再教是覆盖不是叠加、能删。

### 三条已知短板

1. **只对它被纠正过的问题生效**。没教过的地方照样会错——这不是「学会思考」，是「记住答案」。
2. **匹配是字面不是语义**。「白系ap」教过之后，问「舞萌那首歌代打」还是不会命中。要语义得走向量，但那就回到了错杀风险。
3. **表会一直长**。现在是留最近 500 条自动淘汰；如果以后纠正量大到几千条，得改成「按命中率淘汰」（从没被用过的先扔）。

## 记忆搬到服务端（A2 v0.3，2026-11-12）

用户原话：「能不能让它自己记得，我现在有钱了，不用再删除它的记忆了。」

### 以前为什么是「只存浏览器内存」

v0.2 那版把上下文放在前端 `HISTORY` 数组里，每次请求拼成 `history=` 参数传上来。能解决指代，但三个硬伤：

1. **刷新即失忆**——关掉页面再打开，它就不认识你了；
2. **换设备即失忆**——手机上问一半，电脑接不上；
3. **客户端说的「上文」本来就不该被信任**——虽然做了 role 白名单和截断，但它终究是外部输入。

### 现在怎么存

新表（`app/db.py`）：

```sql
CREATE TABLE IF NOT EXISTS agent_turns (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    ts TEXT NOT NULL,
    role TEXT NOT NULL,     -- 只有 user / assistant
    content TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_agent_turns_session ON agent_turns(session_id, id);
```

流程：浏览器第一次问 → 服务端生成 `session_id` 并 `Set-Cookie: gb_sess`（HttpOnly）→ 每轮问答写 `agent_turns` →
下次提问从库里取最近 N 轮塞进 messages → 答完 `memory.trim()` 把超过 200 轮的老记录删掉。

`app/memory.py` 只做五件事：`new_session` / `append`（role 白名单）/ `recent` / `turn_count` / `forget` / `trim`。

### 预算放宽了多少（以前全是为了省钱）

| 项 | 以前 | 现在 | 环境变量 |
|---|---|---|---|
| 往回带几轮对话 | 3 | **20** | `AGENT_HISTORY_TURNS` |
| 单条历史截断 | 200 字 | **600 字** | `AGENT_HISTORY_CHARS` |
| 单条检索结果截断 | 120 字 | **240 字** | `AGENT_HIT_CHARS` |
| 一次工具最多几条 | 5 | **6** | `AGENT_MAX_HITS` |
| 最多几轮工具调用 | 3 | 3（故意不动） | `AGENT_MAX_ROUNDS` |

**该放宽的是「记忆」，不是「噪音」——这是量出来的，不是猜的：**

| 工具截断配置 | 50 条正确率 | 误触发 | 平均轮数 | 平均耗时 |
|---|---|---|---|---|
| 120 字 / 5 条（旧） | 49/50 = 0.980 | 0/12 | 1.04 | 7209 ms |
| 400 字 / 8 条（第一版改法） | 47/50 = 0.940 | **1/12** | 0.92 | 2885 ms |
| **240 字 / 6 条（最终）** | **48/50 = 0.960** | **0/12** | 0.90 | 2801 ms |

放到 400 字那组，多出来的一次误触发是「上一条图是谁发的」——本该反问，它却去翻库了。
工具结果越长，它越容易觉得「我该去查一下」。所以工具输出只翻一倍，历史轮数翻了六倍多。
（旧的 120/5 那行 7209ms 是关掉规则前置的基线，不能直接跟后两行比耗时。）

### 代价，说清楚

历史从 3 轮变 20 轮，prompt 会长几倍；命中截断从 120 字变 400 字，工具结果也长几倍。
**这不是免费的**，一次问答的 token 可能是原来的 3–5 倍。用户明确表示接受（「我现在有钱了」），
但所有值都能在 `.env` 里用上面那几个变量拧回去，不用改代码：

```bash
# /opt/group-brain/.env
AGENT_HISTORY_TURNS=6
AGENT_HIT_CHARS=200
```

### 留了一个能删的按钮

「不用删记忆」不等于「删不掉」。`POST /api/agent/forget` 清空当前会话，
`/agent` 页脚有个不显眼的「清空记忆」小按钮——它是保险丝，不是功能。

### 已知短板

- **表会一直长**。每个 session 最多留 200 轮、单条最多 2000 字，但没有「全局清理」定时任务；
  目前靠 `forget` 手动清。会话多了以后这张表会变成库里第二大的表（第一是向量）。
- **记忆是「这台浏览器的」**，不是「你的」。换浏览器/隐身模式就是新会话——
  要真正做到「跟人走」，得先有登录体系，那是另一个项目。
- **没做跨会话引用**：「上次我们聊的那个」只能看到本 session，老会话里的内容还得靠检索。

## 事实记忆：它知道什么，由人点头决定（A2 v0.4，v0.14）

纠错改的是「这一次的回答」，事实改的是「它知道什么」。

```
群聊 564 条 ──▶ scripts/extract_facts.py ──▶ facts 表 pending ──▶ /facts 点头 ──▶ approved + 重建 FTS
                 （模型出草稿）                （检索不到它）        （采纳/拒绝/退回）    （立刻能查）
```

### 表结构

```sql
CREATE TABLE facts (
    id INTEGER PRIMARY KEY AUTOINCREMENT, ts TEXT NOT NULL,
    subject TEXT NOT NULL,        -- 谁 / 什么
    claim TEXT NOT NULL,          -- 一句话结论
    quote TEXT,                   -- 支撑它的原话片段（没有这个字段就是谣言）
    msg_ids TEXT,                 -- 来源消息 id
    status TEXT DEFAULT 'pending',-- pending / approved / rejected
    hits INTEGER DEFAULT 0,       -- 被引用过几次（用来发现「这条其实很有用」和「这条在污染」）
    decided_at TEXT);
CREATE VIRTUAL TABLE facts_fts USING fts5(bigram, fact_id UNINDEXED, tokenize = "unicode61");
```

### 为什么必须有人工这一步

抽取是模型猜的。一条猜错的事实（「147 爱吃鱼片」其实只是他问过一次）会被当成「群里的常识」反复引用——**一次答错只错一句，一条脏事实会错一片。**

所以分工是：**模型出草稿，人负责点头**。`pending` 的事实检索不到，也就影响不了任何回答；点头之后才重建 FTS、才进 `search_facts`。

### 三个实现上的决定

1. **prompt 从「严格」改成「宁可多抽」**：第一版写着「宁缺勿滥」，跑 60 条抽出 0 条。查原始输入——前 21 条全是 bot 自言自语，抽不出是对的；但换成人类发言仍 0 条，说明严格过头。放宽后同段抽出 3 条可用草稿。
2. **两级去重**：`subject|claim` 全等算重复；同一 subject 下 claim 二元组 Jaccard ≥ 0.70 也算（「口头禅是杂口杂口和扎口」vs「常用扎口扎口作语气词」）。不去重，待审列表会被同一件事刷屏，审的人第一次就烦。
3. **事实检索没有向量那一路**：几十条人工点头过的短文本，关键词够用；算向量是给自己找活儿干。

### 踩到的两个坑

- **`to_bigrams()` 返回的是空格串不是列表**。写成 `for bg in to_bigrams(text)` 会按**字符**遍历，索引里全是单字，而查询 token 是二元组 → 永远查不到。修法 `.split()`。同一个 bug 我在写索引和查索引两处各犯了一次，本地批准一条「147｜爱喝扎啤」却查不到才露馅。
- **新工具会带坏旧行为**：加了 `search_facts` 之后，同一份 50 条从 49/50 掉到 46/50，四条失败全是「多调了 search_facts」。根因是工具描述写成了广告（「先调它，不行再调 search_memory」）。修法两条：描述改成「只在这两种时候调它」，并且**0 结果时在 payload 里明说「不要再调 search_facts」**——模型的下一步动作可以被工具返回值引导，这比在评测脚本里加规则管用。修完回到 48/50。

### 怎么用

```
python scripts/extract_facts.py --limit 600      # 抽草稿（花钱，几毛）
# 打开 /facts 一条条点头
```

## 规则自学习：规则从数据里来，但要过三道闸门（A2 v0.5，v0.15）

手写正则靠我读评测集，加一条要改一次代码。这一层把规则变成数据：挖、测、人点头、可停用、可删。

```
eval/agent_cases.jsonl (50 条) ──▶ 挖 n-gram 候选 ──▶ 支持度≥2 且 纯度≥0.99
                                                        │
eval/agent_holdout.jsonl (10 条) ──▶ 影子测试：准确率不许降，且准确率或前置率有提升
                                                        │
                                              rules 表（enabled=0）──▶ /facts 页点头 ──▶ enabled=1 参与前置
```

挖出来三条：`有人说过` → search_memory、`的表情包` → search_meme、`天有` → get_time + search_memory。

**老实说结果**：留出集 10/10 → 10/10（被前置的题 7 → 8 条）；50 条主集规则开关各跑一次，准确率都是 48/50，平均轮数 0.90 → 0.94、耗时 2226 → 2504 ms（噪声范围内）。所以它的价值不是「变准」，是**省一次往返**，以及把「规则」从代码变成可审计的数据。等评测集上千条时，这个差别才会显出来。

## 记忆跨设备：记忆跟着口令走（v0.16）

v0.13 的记忆存在服务端，但绑的是**浏览器 cookie**：手机上问过的，电脑上打开是新会话。理由当时写的是「防止别人用同一个浏览器串台」，实际上这个顾虑不存在——能打开页面的人本来就有口令。

改法（`AGENT_SHARED_MEMORY`，默认开）：

```
请求进来 ──▶ _agent_session(request)
              │
              ├─ 共享模式：先 memory.adopt_into() —— 如果 "main" 还是空的，
              │            把「最近活跃的那个 cookie 会话」整段搬过来
              │            （目的：升级后别让人觉得「它把我的对话忘了」）
              │            然后一律返回 ("main", False)
              │
              └─ 兼容模式（AGENT_SHARED_MEMORY=0）：读 gb_sess / 新建，行为同 v0.13
```

代价与取舍：

- **一个站点只有一段记忆**。想隔离只能关掉开关回到 cookie 模式；真要多人用，得加用户表，那是另一个项目。
- 「清空记忆」现在是**全局**的（手机点一下，电脑上也没了），所以按钮文案改成了「手机、电脑上看到的是同一段，一起清掉」。
- `adopt_into` 只搬一次，而且挑的是 `MAX(id)` 最大的那个会话——搬错的风险是「把测试会话搬进来」，所以我用它之前先在本机验过一遍（3 条旧会话 → `main` 里 5 条，含新问的一轮）。

## 事实自动审阅：让机器只处理它能确定的那部分（v0.16）

线上待审堆积到 211 条，人一条条点会放弃。但「自动点头」很容易变成「全放行」，我踩了两次：

| 版本 | 判据 | 结果 | 问题 |
|---|---|---|---|
| 第一版 | 原话能在引用消息里查到 + 带 id + 主语是群成员 | 140 条里过了 **138 条** | 抽取本来就抄原话，「能查到」只证明没编 |
| 第二版 | 再加「原话至少 8 个字」 | 10 条，把「147｜想吃鱼片」也毙了 | 原话短 ≠ 事实假 |
| 第三版（现在） | 原话可查 → 主语必须真人 → 结论不能讲机器人/指令 → **结论的二元组要能在「原话 + 引用消息」里找到 ≥50%** | 线上 211 条 → 自动点头 10 / 自动拒绝 83 / 留给人 118 | 支撑度是从 35% 提上来的，见下 |

支撑度从 0.35 提到 0.5 不是拍的：「还来污染管理员了」会被读成「是群管理员」、「ig」会被读成「看好IG」。**推断留下的代价比漏掉一条大得多**——`search_facts` 会把它们当事实喂给模型，答错一句会被当成依据反复引用。

第三版的分档规则（`app/facts.py: score()`）：

- `≥11` → 自动点头（`auto=1`），实际要求「原话可查 + 主语真人 + 支撑度 ≥60% + 结论长度正常」
- `≤3` → 自动拒绝（`auto=2`）：原话查不到、主语是 bot、结论只在讲「相关/提到」
- 中间 → 留给人，这些正是「机器拿不准」的部分

同一个主语下结论相似度 ≥0.75 的，自动点头时只留一条（避免「设置了每日重置**使**鱼忘记扎口」和「…**导致**鱼忘了扎口」并存）。

```
python scripts/review_facts.py                 # 只看（默认 dry-run）
python scripts/review_facts.py --apply --reject-junk   # 点头 + 清垃圾
python scripts/review_facts.py --undo-auto     # 一键全退回（人工点过的 auto=0 不动）
```

**为什么保留「留给人 70 条」**：事实层错的代价不是答错一句，而是被反复当依据引用。机器能确定的（谁说的、原话在不在、主语是不是机器人）放手给机器；「这算不算一条事实」必须人点头。自动处理只是把人的工作量砍一半，不是替人判断。

## 联网检索：给它一双眼睛（v0.18，2026-11-16）

### 为什么要做

用户的原话是「让它直连互联网，自己去找资料，这会比我们在这里填提示词来的正确」。他说得对：前面九种检索手段（多查询扩展、HyDE、record 改写、PRF、相邻拼接、reranker、句意索引、同字扩展、语料接地）都是在**已有的 572 条记录里翻**，而「Python 3.12 什么时候发布」这类问题，答案根本不在群里——不是检索不行，是**它没有眼睛**。

### 通道选型（本机 + 杭州服务器都实测过）

| 通道 | 本机 | 服务器 | 要 key | 结论 |
|---|---|---|---|---|
| `cn.bing.com/search` | 200 / 1.1s | 200 / 0.3s | 否 | **默认** |
| `www.baidu.com/s` | 200 / 1.2s | 302（风控跳转） | 否 | ✗ 不稳 |
| `html.duckduckgo.com` | 超时 | 超时 | 否 | ✗ 国内不通 |
| `api.tavily.com` | 200 | 200 | 是 | 有 key 就优先用它 |
| `api.search.brave.com` | 超时 | 超时 | 是 | ✗ 不通 |
| `zh.wikipedia.org` | 超时 | 超时 | 否 | ✗ 不通 |

默认就是「抓 Bing 中文结果页」。这条路没有合同、没有 SLO，Bing 一改版就断，所以：

1. 解析失败一律返回空列表，**绝不抛异常把整轮对话弄挂**（和 `search_facts` 的 0 结果同一个原则）。
2. `TAVILY_API_KEY` 存在时优先用 Tavily（结构化 JSON、质量更稳），Bing 只做兜底。
3. 结果进 `web_cache` 表，同一个问题一小时内不再打网络——省时间，也让评测可复现。

### 两个工具

| 工具 | 用途 | 约束 |
|---|---|---|
| `web_search` | 搜公开资料，返回标题 / 链接 / 摘要（≤220 字） | 描述里写明「只用于群外知识；问群里谁说过什么时不要用它」 |
| `fetch_url` | 抓**一个**页面的正文前 1200 字 | 一次对话最多抓 2 个页面；只放行公网 http/https |

**为什么还要 `fetch_url`**：摘要只够判断「是不是这个」。实测问「Python 3.12 什么时候发布的」，Bing 摘要里只有「Welcome to Python.org」，模型于是自己换了个英文查询词、再抓 `python.org/downloads/release/python-3120/` 才拿到 2023-10-02。够用，但也说明**摘要经常不足以回答具体数字**。

**SSRF 防护**（`_safe_target()`）：只认 http/https，端口只认 80/443，域名解析出的 IP 必须在公网段。理由很实际——服务器上跑着 AstrBot、Docker 和内网 172.22.x.x，如果模型被诱导去 `fetch http://127.0.0.1:8000/api/admin/run`，那就不只是答错话的问题了。

### 评测（`eval/agent_web_cases.jsonl`，8 条）

```
OK 1. Python 3.12 是什么时候发布的   实际=search_memory/web_search/web_search/fetch_url
OK 2. FastAPI 现在最新版本是多少     实际=get_time/web_search/fetch_url/web_search
OK 3. Docker Engine 最新稳定版是几    实际=get_time/web_search/web_search/fetch_url
OK 4. 谁说过要吃鱼片                实际=search_memory        ← 该查群，不许上网
OK 5. 群里有人提过 FastAPI 吗        实际=search_memory        ← 问「群里有没有」，不是「FastAPI 是什么」
OK 6. 有没有烧糊的表情               实际=search_meme
OK 7. 今天几号                     实际=get_time
OK 8. 你好呀                       实际=-                    ← 一个工具都不该调
```

**8/8、误触发 0/1、平均 2.12 轮、平均 3481ms**（不联网的题约 1.1–1.8s，联网题 4–6s）。

判分器为此加了一个 `subset` 字段：联网题的正确解可能是「先翻群失败再上网」，也可能是「直接上网」，强行要求工具集合完全相等等于在考我的判分器。

主集（50 条）跑一遍是 **46/50**，看起来掉了，但四条失败里 **没有一条碰到 `web_search`**：两条是重跑就好（方差），两条是老问题（`谁在群里说要减肥` 调 3 次、`上一条图是谁发的` 该反问却去查）。所以加联网**没有带坏原有行为**——这跟当初加 `search_facts` 从 49 掉到 46 不一样，那次是真被工具描述带偏了。

### 已知短板

1. **摘要短、榜单浅**。Bing 前 5 条经常是官网首页而不是具体页，模型得自己再搜一次或抓页面。
2. **没有时效校验**。搜索结果带日期，但没人检查「这条是不是三年前的旧文」。
3. **Bing 会变**。改版就断，断了就是「网上没查到」，不会报错但会变哑。
4. **抓不到 JS 渲染的页面**（只读 HTML）——**v0.18.1 用真浏览器兜底补上了这一类**，见下一节。
5. 群内问题偶尔会先翻一次群聊再上网（case 1 就是这样），多花约 1.5s——`subset` 允许它，但更省的做法是让 SYSTEM 里第 7 条更硬。

## 真浏览器兜底：借主人电脑上的那只眼睛（v0.18.1，2026-11-16）

### 为什么

纯 HTTP 抓不到三类页面，实测数据（服务器上跑，2026-11-16）：

| 页面 | 纯 HTTP | 真浏览器 |
|---|---|---|
| 知乎某个问题页 | **403 / 650 字节** | 204 字（登录墙提示，但至少知道被挡了） |
| 掘金某篇博文 | 200 但只有 2397 字节（JS 壳） | 352 字（正文） |
| StackOverflow 某问答 | **403 / 5758 字节**（CF 盾） | 1200 字（正文，被 `MAX_PAGE` 截断） |
| python.org 发布页 | 1200 字 | 不需要 |

### 架构：为什么要在「主人电脑」上跑

`bsk`（BrowserSkill）驱动的是**他那台 Windows 上、他自己登录态的 Chromium**。服务器在杭州，两者之间没有通路，所以：

```
服务器 app/websearch.py ──HTTP──> 127.0.0.1:8010  ←── SSH 反向隧道 ── 他电脑 bsk_reader.py ──> bsk → 真 Chromium
```

- 他电脑上跑 `Desktop\bsk-reader\bsk_reader.py`（只监听 127.0.0.1:8010，内部 `bsk open` + `observe` 取语义文本）。
- 再跑一条常驻隧道：`ssh -N -R 8010:127.0.0.1:8010 gb`（两个 `.bat` 都在 `Desktop\bsk-reader\`，双击即可）。
- 服务器侧 `cfg.BROWSER_READER`（默认 `http://127.0.0.1:8010`）指向隧道；`fetch()` 先走纯 HTTP，**失败或正文 < 200 字**才转发过去。

### 三个必须写下来的实现细节

1. **`bsk open` 必须带 `--observation`**，值取 `bsk sync --json` 顶层的 `observation_id`（不是 `observe` 返回的那个）；不带就报 `this action needs an explicit current observation`。偶发失败重试一次即可。
2. **`bsk observe` 必须带 `--tab-id`**，否则有时返回空文本（我第一版就是这样，明明页面已加载却读到 0 字）。
3. **`bsk read` 用不了**：他的扩展协议 1.8 < daemon 1.9，`read` / `evaluate` 被禁用。所以自己从 VOM 里抽文字——取所有引号里的可访问名，去掉相邻重复，就得到一份能读的正文。

### 优雅降级

`_reader_health()` 2 秒探活、结果缓存 30 秒。他电脑关着 / 隧道没开 → 探活失败 → `browser_read()` 返回 `None` → 行为和没有这个功能**完全一样**（只是 403 页面抓不到）。`/admin` 的「真浏览器兜底」卡片会显示「通 / 断」，不用 SSH 就能看出隧道状态。

### 实测（线上，2026-11-16）

```
Q: 帮我打开 https://www.zhihu.com/question/19551242 看看里面在讲什么
rounds=1  took=9516.6ms  fetch_url n=1 7863.4ms
answer: 知乎那个页面需要登录才能看，抓到的只有登录页，看不到正文内容。你可以登录后自己打开看，
        或者告诉我标题/关键词，我帮你搜。
```

**这次它没有编**——抓到的就是登录墙，它如实说「被挡了」，而不是假装读过正文。这是这一节最想留下的行为证据。

## 服务器自己开网页：把「开浏览器」这件事搬回服务器（v0.19.1，2026-11-16）

上一节的真浏览器兜底有个根本问题：**浏览器在主人电脑上**。他一关机、一关窗口、一用别的东西把 bsk 的 Agent Window 顶掉，这条能力就没了（报错原文 `error: the session ended because the user closed the Agent Window`）。他的原话是「你需要能够自己打开网页，不会因为我的操作被影响，同时推视频功能不能因为我电脑未开机被限制」。

所以这轮把开网页的能力分成两层，**服务器自己就能跑**：

### 1. 选片完全不需要浏览器了

深读从「整页渲染」改成「B 站官方 JSON 接口」：

| 要什么 | 从哪拿 |
|---|---|
| 标题 / 简介 / 时长 / 分区 / UP / 播放点赞投币收藏弹幕评论数 | `GET https://api.bilibili.com/x/web-interface/view?bvid=…` |
| 热评（按点赞排序） | `GET https://api.bilibili.com/x/v2/reply?type=1&oid=<aid>&sort=2&ps=8` |

实测 **0.3 秒 / 261 字**，含标题、UP、时长、五项互动数据、简介、三条热评：

```
标题：【2026全球总决赛】11月15日 GEN vs BLG | UP：哔哩哔哩英雄联盟赛事｜时长：319:25
播放：2281.4万｜点赞：33.0万｜投币：26.7万｜收藏：10.7万｜弹幕：29.1万｜评论：6.2万
热评：[赞18209] 尺帝真稳呀… / [赞39465] 感觉blg这边中路还是玩法核稳…
```

一个坑：**不带 cookie 的请求会被回 `HTTP 412 Precondition Failed`**（热门列表接口不会，详情接口会）。解法是随便编一个格式合法的 `buvid3/buvid4` 塞进 `Cookie` 头，服务端不校验签名——`curator._uicookie()` 就干这个，进程内复用。

### 2. 一般网页：服务器自己的无头 Chromium

新增 `app/headless.py`：Playwright + `chromium-headless-shell`，装在服务器 `/opt/group-brain/.pw-browsers`（约 126MB），**同一时刻只开一个页面**（`threading.Lock`），只放行 html/css，图片/视频/字体一律 abort，单次 25 秒超时。

`websearch.fetch()` 现在是三条路，从便宜到贵：

```
纯 HTTP（几十毫秒）→ 服务器无头 Chrome（1–6 秒）→ 主人电脑的真浏览器（可选，只在他开着时）
```

前一条拿到够长的正文就立刻返回；`via` 字段会写明这条走了哪条（`http` / `headless` / `browser`）。

**实测（服务器上，2026-11-16）**：

| 页面 | 结果 |
|---|---|
| 掘金博文（JS 壳） | `via=headless`、400 字、5.5 秒 |
| 百度 / example.com | `via=http`、0.1 秒 |
| 知乎问题页 | `via=headless` 只拿到 117 字（未登录的登录墙）→ 需要登录态时仍得靠主人那台机器 |
| python.org / HN | 服务器上的 chromium **连不上**（curl 正常，chromium 侧 TLS 超时），这类站点落到纯 HTTP |

### 3. 运维细节（都踩过）

- 装完 browser 还要装系统库，否则报 `error while loading shared libraries: libatk-1.0.so.0`：`apt-get install -y libnss3 libnspr4 libatk1.0-0 libatk-bridge2.0-0 libcups2 libdrm2 libxkbcommon0 libxcomposite1 libxdamage1 libxfixes3 libxrandr2 libgbm1 libpango-1.0-0 libcairo2 libasound2 libatspi2.0-0 libx11-xcb1`
- 浏览器路径写死在 `headless.py` 里兜底（`/opt/group-brain/.pw-browsers`）：systemd 有 drop-in 传 `PLAYWRIGHT_BROWSERS_PATH`，但 cron、ssh 手测都没有，否则会报 `Executable doesn't exist at /root/.cache/ms-playwright/...`
- 内存：1.7G 内存 + 4G swap，单页 250–400MB，所以并发必须 1；`--single-process --no-zygote --disable-dev-shm-usage` 是省内存的关键
- 服务器上部分境外站点 chromium 连不上（见上表），这不是配置问题，是这台机器的出网策略，**不修**——那些站点纯 HTTP 通常够用

### 结论

「推视频」现在**完全不依赖主人的电脑**（官方接口 + 无头浏览器都在服务器上）。真浏览器那条降级成「需要登录态时的可选增强」：他开着就用，不开也不影响任何定时任务。
