# 路由实验：这活儿到底该不该请大模型

一句话结论：**这项任务上，20 行正则就能拿到和大模型一样的准确率，而大模型贵 18 倍、慢 50 倍。**
真正需要模型的地方只有一处——「指代」，而模型也没解决它。

---

## 1. 为什么做这个实验

A2 把检索包成三个工具交给 DeepSeek 的 function calling，跑出来 30/30。看起来很美好，
但有两个问题一直没回答：

1. **每次对话都先问一遍大模型「要不要调工具」，这钱花得值吗？**
2. 如果要省钱，能不能先用规则挡掉大部分请求？

这就是「小模型路由」这个方向的价值：不是为了让模型更聪明，是为了让**大部分请求根本不进模型**。

---

## 2. 四个方案

| 方案 | 做法 | 备注 |
|---|---|---|
| `rule` | 20 行正则：寒暄 → 不调；含「图/表情」→ search_meme；纯问时间 → get_time；含「谁/说过/提过」→ search_memory | 0 元、0 毫秒 |
| `small` | 硅基流动免费池的 Qwen2.5-7B，一次调用直接输出 `{"tools": [...]}` | 0 元，但会排队 |
| `big` | `deepseek-chat`，同样的提示词 | 按 token 收钱 |
| `route` | 规则有把握就用规则 → 没把握（含指代词、规则没命中、短句）问小模型 → 小模型也崩了才问大模型 | 三级降级 |

判分只有一条：**工具集合是否和期望完全相等**。不判回答好不好（那是 `EVAL.md` 第七节的事）。

```bash
python scripts/bench_routing.py                                  # 训练集 50 条
python scripts/bench_routing.py --cases eval/agent_holdout.jsonl  # 留出集 10 条
```

---

## 3. 结果

### A. 训练集（50 条，规则是看着这批题写的，等于开卷）

| 方案 | 正确率 | 平均延迟 | 每千次成本 |
|---|---|---|---|
| rule | **47/50（94%）** | **0 ms** | **¥0** |
| small | 42/50（84%） | 2234 ms | ¥0 |
| big | 47/50（94%） | 3042 ms | ¥0.73 |
| route | 47/50（94%） | **60 ms** | **¥0.039** |

`route` 的 50 次里，47 次由规则直接答掉、3 次降级到小模型、**一次都没用到 DeepSeek**。

### B. 留出集（10 条，写完规则之后才写的题）

| 方案 | 正确率 | 平均延迟 | 每千次成本 |
|---|---|---|---|
| rule | 10/10 | 0 ms | ¥0 |
| small | 9/10 | 779 ms | ¥0 |
| big | 10/10 | 3314 ms | ¥0.73 |
| route | 10/10 | 59 ms | ¥0.068 |

**留出集 10 条什么都证明不了**——样本太小，且题型和训练集同源。它只能说明「换一批说法，规则没有立刻崩」，
不能说明规则能泛化。想真证明，得让另一个人写 50 条我完全没看过的题。

---

## 4. 五条结论

### ① 先写规则，再谈模型

`rule` 94%，成本 0，延迟 0。**在这类「关键词能覆盖大半」的路由任务上，模型加的钱买不到准确率。**
`big` 和 `rule` 打成平手（都是 47/50），但贵 18 倍、慢 50 倍。
所以工程上的正确顺序是：先把手写规则写到 90%，剩下的 10% 才轮到模型——而不是上来就 function calling。

### ② 剩下的 3 条错误全是同一个原因：指代

三条错题：`刚才那句话是谁说的` / `上一条图是谁发的` / `他昨天不是说要去睡觉了吗`。
规则错、小模型错、大模型也错——**四个方案错法一样，都是「假装听懂了」去瞎搜**。

这不是模型不够大能解决的，是**接口设计**的问题：
`/api/agent?q=` 是单轮接口，模型真的拿不到「刚才那句」是哪句。正确行为是反问「你说哪句」，
而不是搜一个看起来像的词然后编一个答案。**要修的是接口（带上最近几条对话），不是模型。**

### ③ 小模型的真实短板是「格式」和「相对时间」,不是「理解」

- 50 条里有 **2 条 JSON 直接解析不出来**（`有人要剁我尾巴？`、`谁说话最多`）——
  弱模型不是答错，是根本不按格式回。工程上所以要 `_parse_tools()` 兜底 + 降级。
- 相对时间全错：`昨天有谁在群里说话` 只给 `search_memory`，不给 `get_time`（4 次里错 4 次）。
  大模型 4 次里对 3 次。

结论：小模型适合「照格式打标签」，不适合「需要常识推理的复合判断」。

### ④ 分级路由的收益在「延迟和钱」，不在「准确率」

`route` 和 `rule` 准确率一样（94%），但它证明了架构可行：**94% 的请求不进模型**。
真实场景里 request 量越大，这个差别越是钱和体感：
- 每千次：¥0.73（全走大模型）→ ¥0.039（路由），省 95%
- 平均延迟：3042 ms → 60 ms

### ⑤ 这个任务已经饱和了，别再拿它当「AI 能力」的证明

50 条里 47 条靠正则就能对。继续在这份题上调参只是在拟合我自己的写法。
下一步要么换更硬的题（真实对话、指代、多轮），要么承认它是「路由」而不是「理解」。
`1.000` / `94%` 这种数字，永远要说清楚是在哪份题上。

## 5. 所以代码该怎么改（还没改，先记着）

1. `/api/agent` 接受一个 `history` 参数（最近 3 条对话），让指代有东西可指——
   这是唯一能真正提升准确率的一步，且不花钱。→ **已实现**（A2 v0.2，指代题 0/6 → 6/6）
2. `agent.run()` 前面加一层 `rule_route()`：规则有把握就直接执行工具、跳过模型决策。
   注意**只跳过「决定调不调」，不跳过「怎么回答」**——回答还是要模型写。
   → **已实现**（`app/router.py` + `app/agent.py` 前置，同一份题 7209 ms → 4661 ms）
3. 小模型只用于「规则没命中」的兜底，且必须给 `_parse_tools()` 兜底，解析失败就退大模型。
   → 仍未实现：实测规则 low 的情况只有 12/50，为这点比例引入一个网络依赖不划算。

落地细节与踩坑见 `docs/agent.md` 的「规则前置」一节。一句话总结：
**没有测量过的优化不算优化**——第一版前置就是没测就上，结果净亏。
