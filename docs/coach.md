# A4 学习教练：周报是「先算事实，再让模型写」

## 一、它想验证什么

前面三个模块（A1 检索、A2 Agent、A3 路由）都是**模型在主导**：给工具、给它判断空间。
A4 反过来——**我先算好这一周发生了什么，模型只负责把事实组织成人话。**

这个顺序不能反。让模型「自己去 GitHub 看看我这周干了啥」，它会编：编得像真的，还很难查。
所以这一节真正想验证的是：**把事实提取和语言组织拆开，能不能得到一份「每句都有出处」的周报。**

## 二、事实从哪来

只有两个来源，都是可核对的：

| 来源 | 拿到什么 | 怎么拿 |
|---|---|---|
| GitHub | 这一周的提交（sha / 第一条信息 / 时间） | `GET /repos/zkysever/group-brain/commits?since=&until=`，最多 3 页 |
| 群聊 | 有几天有人说话、一共几条、最热闹哪天、说话最多三个人 | 只对 `messages` 做 `GROUP BY`，**不取任何一句原文** |

从提交里再推两样东西，都是正则，不花钱：

- `fix_like`：`fix|修|回退|revert|又|再次|还是|没生效` —— 这些词往往就是「卡在哪」的线索
- `touched_hint`：提交信息里出现过的文件名

`render_facts()` 把清单拍成**一段纯文本**，不用 JSON。理由很实际：模型对着 JSON 容易照着念字段名（“commits 数组长度为 19”），对着人话才会写人话。

## 三、模型被允许做什么

`SYSTEM` 五条，其中两条是硬的：

1. **只能用清单里的事实。清单里没有的东西，一个字都不许加。**
2. 三段，每段一两句，总计不超过 260 字：这周做了什么 / 卡在哪 / 下周一件具体的事。
3. 卡点要从事实里推，不许硬凑（没有就写「没有明显卡点」）。
4. 下周那件事要能直接开始做，不要「继续深入」这种废话。

## 四、怎么用

```bash
# 网页（要口令）：生成 / 重算某一周
https://zkysever.com/coach

# 命令行
python scripts/gen_report.py --week 2026-W46
python scripts/gen_report.py --week last        # 上一周
python scripts/gen_report.py --dry              # 只打印事实清单，不调模型、不落库

# 每周一 02:00 自动生成上一周（可选）
0 2 * * 1  cd /opt/group-brain && .venv/bin/python scripts/gen_report.py --week last
```

接口：

| 方法 | 路径 | 干什么 |
|---|---|---|
| GET | `/api/coach?week=2026-W46` | 读。返回该周周报（可能没有）+ 最近生成过哪些周 |
| POST | `/api/coach?week=2026-W46` | 写。生成或重算，**要调一次 DeepSeek，10~20 秒** |

**为什么生成必须是 POST**：它花钱、也慢。做成 GET 的话，刷新一次页面就重新扣一次钱——这不是一个页面该有的行为。

## 五、留档

`reports` 表存四样东西：`week`（ISO 周，主键）、`facts`（喂给模型的那份清单）、`text`（正文）、`model`（哪个模型写的）。

存 `facts` 的唯一目的是**对账**：报告里的每一句，都应该能在 facts 里找到出处。哪天真发现它在编，把这两列拿出来一比就知道。

## 六、实测

**2026-W45**（只有 1 次提交）：

> 一、11 月 5 日提交了 v0.1 群聊记忆体 MVP，包含关键词检索、表情包入库、评测脚本三块。
> 二、没有明显卡点。只有一次提交，没有回退或反复修改的痕迹。
> 三、把评测脚本跑一遍，记录关键词检索在现有群聊数据上的命中情况。

**2026-W46**（19 次提交）：

> 一、11-09 一天里从 v0.2 推到 v0.5.1……评测集从 16 条扩到 50 条，定稿基线 Recall@5 0.938 / MRR 0.899。11-10 做 A2 的 history（指代题 0/6 到 6/6）、A3 路由实验（20 行正则和 deepseek 打平，便宜 18 倍快 50 倍）……
> 二、v0.5 里 RRF 融合写了两遍要回头修，v0.5.1 又修线上 500，检索这块是边接边返工。sshd 配 2222/443 时踩了 Port 覆盖式、22 被冲掉的坑。
> 三、把 A3 那 20 行正则路由接进 /api/agent……

两条值得注意的地方：

- W45 那次没有硬凑卡点，直接写「没有明显卡点」——这是规则 3 起了作用。
- W46 的「卡在哪」两处都指得准（融合两遍、500 事故、sshd），而且都能在 facts 的 `fix_like` 里找到对应。

## 七、已知短板（写清楚，别假装没有）

1. **只有 commit message 一个信号源。** 没有 diff、没有 issue、没有视频进度。所以「改了多少」它说不准，只能说「改了什么名字」。
2. **空数据会被忽略**。W46 群聊是 0 条（数据只到 11-05），报告里一个字没提。这不算编造，但也不够诚实——将来应该在 facts 里显式写一句「本周群里没人说话」。
3. **周报不是评测**。A2 的正确率是跑出来的，A4 的正文好不好，目前只能人看。想量化得另造一套「事实里有没有出现编造的数字」的检查。
4. **没有推送**。现在只能自己打开网页看。推群或推微信是下一件事，不是这一件。

## 八、三条教训

1. **AI 功能里最贵的不是模型调用，是你搞不清它在说什么。** 所以 `facts` 必须留档。
2. **让模型「总结」之前，先替它把事实算好。** 这一步省下来，省的是你后面查它有没有编的时间。
3. **生成要花钱的接口，别做成 GET。**
