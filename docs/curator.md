# B 站选片：先看简介和评论，值得才深读，最后推到 QQ（v0.19）

> 需求原话（2026-11-16）：「使用哔哩哔哩时先看评论和简介，如果符合再观看视频，不是我不让用，主要是有点贵，你可以把感觉好看的视频用 QQ 发给我链接，每天你最多能看三个视频，但如果你觉得简介和评论很有意思也可以发给我，你在早上 8 点到晚上 11 点每隔一个小时都可以给我推一个视频」

## 一、为什么这么设计

B 站视频本身读不了（没有画面理解），能读的是**页面上的文字**：标题、简介、评论区。于是把「看视频」拆成两档：

| 档 | 干什么 | 靠什么 | 成本 |
|---|---|---|---|
| 看一眼（默认） | 标题 + 简介 + 互动数 + 热评 | 公开 JSON 接口，免登录 | 几乎为零 |
| 深读（每天≤3 次） | 用真浏览器把视频页整页读一遍 | `ssh -R 8010` → 主人电脑上的 Chromium | 慢（几秒）、要主人的电脑开着 |

「有点贵」对应的是第二档：深读要经过他电脑上的浏览器，慢且不能滥用，所以每天 3 次。
第一档完全免费，所以每个小时都能跑。

## 二、三段漏斗

```
热门列表(50 条, 免登录 JSON)
      │  去掉处理过的
      ▼
按互动率粗筛 → 前 8 条
      │  每条拉 8 条热评（另一个免登录 JSON）
      ▼
DeepSeek 打分 1~5（带理由和「一句话」）
      │  ≥4 分才推；=5 分直接停手
      ▼
深读（≥4 分且今天没超过 3 次）
      ▼
写 outbox/*.json  →  AstrBot 插件 → 他的 QQ 私聊
```

打分标准写死在 `app/curator.py` 的 `_PROMPT` 里：5=有真东西值得专门找时间看；4=有意思随手推不亏；3=一般；2=标题大于内容；1=别浪费时间。并明确告诉模型**播放量高不等于好**，评论区在讨论技术细节/剧情/事实要加分。

## 三、为什么推送是「写文件」

group-brain 在宿主机 systemd 里，QQ 在 Docker 的 AstrBot 里，两边没有共享的 HTTP 口子。但 `/opt/qqbot/astrbot-data` 同时是宿主机目录和容器的 `/AstrBot/data`，所以：

```
group-brain  →  /opt/qqbot/astrbot-data/curator/outbox/*.json
AstrBot 插件 →  /AstrBot/data/curator/outbox/*.json  （同一个目录）
                发完移到 sent/，失败 3 次移到 failed/
```

这比「服务器调 AstrBot 的 HTTP」稳：不需要开端口、不需要反代、AstrBot 重启也不丢消息（文件还在）。

## 四、限额（都是硬约束）

| 约束 | 位置 | 说明 |
|---|---|---|
| 每小时最多 1 条 | `curator.pushed_within_hour()` | 用 `curator_items.pushed_at` 的 MAX 判断 |
| 每天最多深读 3 次 | `curator.deep_used_today()` | 数 `deep_at` 当天的行数 |
| 只在 08:00–22:59 跑 | crontab `0 8-22 * * *` + `in_window()` | 两层都挡，防止手动执行时越界 |

`--force` 只跳过「窗口」和「每小时一条」，**不跳过深读 3 次/天**——那才是花钱的部分。

## 五、文件与命令

| 文件 | 作用 |
|---|---|
| `app/curator.py` | 全部逻辑：取数、拉评论、打分、深读、限额、写 outbox |
| `scripts/curator_run.py` | 命令行入口（面板按钮 / cron 用） |
| `tools/astrbot_plugin_qq_curator/` | AstrBot 插件：轮询 outbox → 发 QQ → 归档 |

```bash
# 手动跑一轮（受限额约束）
python scripts/curator_run.py
# 无视窗口和每小时限额，只判断不推送
python scripts/curator_run.py --force --dry
# 面板上：管理面板 → 「跑一轮 B 站选片」
```

接口：`POST /api/curator/run?force=&dry=`、`GET /api/curator/list`。

## 六、首次实测（2026-11-16）

- 本机 dry-run：8 条候选全部打分成功，最高分 `BV15es76gEgL`（2026 全球总决赛 GEN vs BLG）4 分，理由「完整赛事录像，评论在讨论中单法核与法刺的战术取舍，有真实内容」；其余 7 条 2 分，理由多是「情绪向整活 / 标题大于内容 / 评论全是玩梗」。
- 服务器 `--force` 一轮：写 outbox 成功；插件 60 秒内取走、`已推送 BV15es76gEgL 到 qqbot:FriendMessage:3750575880`，文件进 `sent/`。
- 深读那一步失败：`RuntimeError: error: the session ended because the user closed the Agent Window` → 纯 HTTP 回落也拿到 `HTTP 412`（B 站对无 cookie 的直连会拦）。**结论：深读只是加分项，失败不影响推送**；想要稳定深读，主人的浏览器窗口要一直开着。

## 七、已知短板

1. **热门列表会阶段性地被同一件事占满**（比如世界赛当天 8 条里 7 条是同一个赛事），这时要么推那一条，要么等下一小时；不去人为加权，因为「多样性」是个更难的题目。
2. **评论只取前 8 条按点赞排**，高赞往往是玩梗，真正有信息量的长评可能在第 2 页。
3. **打分是单条独立打**，没有跨候选比较（所以会出现「这小时最差的一条也比上一小时最好的一条分高」的情况，但限额挡住了）。
4. 深读依赖主人的电脑和浏览器会话，关窗口就退化成「只看简介+评论」。
5. 推送是单向的：他回「不好看」不会被记住（要变成学习信号，属于第 2 层「纠错记忆」的活，见 `docs/agent.md`）。
