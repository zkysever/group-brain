群聊记忆体 group-brain

把一个 QQ 群两年半的废话，做成一个能搜索、能回答、能自己维护的网站。
关键词 + 向量混合检索 → 交给大模型自行决定查不查 → 全部跑在一台 2 核 2G 的服务器上。

它现在能做什么

  • 搜索：搜「大肥鱼」能搜到谁喊过、谁吃过鱼片；搜「生气的表情」直接出图。
  • 看上下文：任何一条消息都能展开前后几条，单看一句废话、配上前后文才有意思。
  • 问它：/agent 里问「谁说过要吃鱼片」，它自己决定去翻库、翻图库、还是看表，并把调用过程摊开给你看。
  • 维护：/admin 五个按钮重建索引、重导表情包、建向量、合并 WAL、VACUUM，不用登服务器敲命令。

四个当时想清楚了的决定

一、不用向量数据库，暴力点乘就够了。

605 条 × 1024 维 = 2.5MB，全放内存里算一遍余弦相似度是几毫秒的事。 上 Chroma / Milvus 能让架构图好看，但要多跑一个进程、多一份要备份的状态， 在这个量级上纯粹是给自己找活儿干。什么时候该换？等它慢到 100ms 以上再说，那时数据量大概在十万条。

二、中文用 bigram 切分，不用 jieba。

「大肥鱼」切成「大肥 / 肥鱼」，搜「肥鱼」也能中——牺牲一点精度，换来零依赖、零词典、 可解释。第一版就是这样拿到 Recall@5 0.938 的。词频统计的毛病它也有：搜「开盒」搜不到「开个盒」， 这类问题后来靠向量补上了。

三、融合只做一次。

RRF 只记名次：每条记录贡献 1/(60+名次)。我第一版先把「关键词 × 向量」融合一遍， 再和表情包融合第二遍——结果向量里排第 1 的消息，第二轮被表情包挤掉了。 改成四路平铺、只融一次之后，Recall@5 从 0.958 涨到 1.000。融合是「定一次名次」的操作，不能嵌套。

四、先写规则，再谈模型。

20 行正则和 deepseek-chat 在「该不该调工具」上打平（都是 94%）， 但一个 0ms、一个 3042ms，一个免费、一个每千次 0.73 元。 最后的分级路由 94% @ 60ms：规则有把握就用规则，没把握（比如出现「刚才那个」）才请模型。

一次线上事故，和它教我的事

上线第一天，所有读库的接口集体 500，但首页好好的。日志里只有一行：

sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread.

原因是我用了一个进程级全局 sqlite 连接，本地单线程手测一切正常，一上线 FastAPI 把同步接口丢进线程池， 第二个线程拿去用就炸了。改成 thread-local 之后，12 线程并发 36 次请求零 5xx。

三条教训，写在 docs/deploy.md 里：本地跑通只等于单线程跑通； 探活不碰库，就不能证明服务好（我就是被一个永远 200 的 /api/health 骗了半天）； 先看 journalctl，别猜。
